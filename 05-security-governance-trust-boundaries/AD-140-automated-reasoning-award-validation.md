# AD-140 — Bedrock Automated Reasoning Checks for Award Decisions (REQ-S606)

**Theme:** Security, Governance & Trust Boundaries
**Catalog:** AD-140 · **Source PRD:** PRD-005 · **Status:** Accepted · **Related:** AD-43, AD-137, AD-141

## Context

PRD-005 §10.7's REQ-S606 has specified Bedrock Guardrails Automated Reasoning checks on Award & Comms Agent outputs since the v1.1.0 ATLAS uplift, validating award decisions against a procurement policy ruleset (approved supplier list, spend threshold, ESG minimum). AD-43 — the ADR that scoped the live Guardrail's actual policy content (content filters, PII, regexes, topics) — never included this control; PRD-005 v1.9.1's changelog explicitly left it "unbuilt pending a ruleset-authoring spike." This ADR is that spike.

Two facts, confirmed by tracing the codebase before writing any rules, shaped the design:

1. **The award decision has no live LLM call to attach a per-call check to.** Node 5 (`orchestrator/node_bid_evaluation.py` + `orchestrator/scoring.py`) computes the award decision deterministically; Node 7 (`orchestrator/node_award_comms.py`) generates notification bodies via inline f-string templates, not an A2A call to the `award_comms_llm` agent. That agent exists as a standalone, deployed A2A skill, but is not on Node 7's current synchronous critical path (removed for latency, per that module's own docstring). Automated Reasoning checks validate LLM-*generated* text for logical consistency with a policy — there is no such generated text on the award-decision critical path today.
2. **The Guardrail is fleet-wide, with no per-agent override.** `buyer_agent_core.factory.DynamicAgentFactory.build` attaches one shared `GUARDRAIL_ID`/`GUARDRAIL_VERSION` (from `infra/agent_runtimes.tf`) to every one of the 6 LLM agents' `BedrockModel` calls uniformly — there is no mechanism in this codebase for a second, agent-scoped guardrail without adding a new per-agent injection path.
3. **The real policy rules already exist in code**, not just in the PRD's prose: `evals/governance_policy_compliance.py:check_governance_policy` checks exactly six things at award time — budget ceiling, approved-supplier membership, ESG minimum, spend-threshold/auto-approval-tier consistency, max negotiation rounds, and confidentiality (no leak in a supplier communication). This is the actual, already-encoded procurement policy ruleset REQ-S606 asks to formalize — not an invented threshold set.

## Decision

**Ruleset.** `security/automated_reasoning_policy.json` hand-authors an Automated Reasoning policy definition (variables, types, rules — the `policyDefinition` schema the Bedrock API defines) directly from `check_governance_policy`'s six checks, as six `if-then` implications plus five non-negativity sanity/boundary rules (per AWS's own Automated Reasoning authoring guidance: bare assertions are appropriate only for boundary conditions). This is loaded via `StartAutomatedReasoningPolicyBuildWorkflow`'s `IMPORT_POLICY` workflow type — which loads a supplied definition as-is — rather than the default document-extraction workflow, since the rules were authored directly from source code, not extracted from prose by an LLM.

**Wiring.** `hashicorp/aws`'s `aws_bedrock_guardrail` resource has no `automated_reasoning_policy_config` argument (confirmed against the provider's current docs) — Automated Reasoning has no Terraform resource in this provider yet, though the raw `UpdateGuardrail` API supports `automatedReasoningPolicyConfig`. `scripts/deploy_automated_reasoning_policy.py` deploys it out-of-band via boto3, the same pattern `scripts/update_skill_runtime.py` already established for AgentCore attributes Terraform can't reach — creating the policy resource, running the `IMPORT_POLICY` build, publishing a version, and attaching it to the live guardrail's DRAFT via `UpdateGuardrail` (a full-replace API, so the script re-fetches and re-passes every other policy config unchanged, the same discipline `update_skill_runtime.py` uses for `update_agent_runtime`).

Because the guardrail is fleet-wide (fact 2 above), the policy is attached to the one shared `aws_bedrock_guardrail.buyer_team` rather than a new second guardrail resource — "applied specifically on Award & Comms Agent invocations" is achieved by the policy's own variable semantics (its rules are inert unless assessed content actually asserts award-decision-shaped claims), not by call-site scoping. Building true per-agent guardrail scoping is out of scope for this ruleset-authoring pass; see Trade-offs.

**Alarm.** `buyer_agent_core.guardrail.has_automated_reasoning_violation` inspects the guardrail assessment tree for any `invalid`/`impossible` `GuardrailAutomatedReasoningFinding` (the two outcomes meaning assessed content actually contradicts policy, as opposed to `satisfiable`/`tooComplex`/`noTranslations`/`translationAmbiguous`, which are inconclusive). `serve.py`'s `_emit_automated_reasoning_failure` calls it at both guardrail-trace capture points (non-streaming `run()` and the streaming executor), unconditionally alongside the existing block/masking check — orthogonal policy dimension, not gated on a hard block having occurred. `aws_cloudwatch_metric_alarm.automated_reasoning_failed` (`infra/bucket_a_alarms.tf`) alarms on `security.automated_reasoning.failed` (Metrics Insights `SUM`, matching `guardrail_triggered_recon`/`memory_write_rejected`'s shape) and routes to `alerts_critical_topic_arn` — the same critical tier `governance_confidentiality_violation` uses.

## Alternatives Considered

- **Build a second, award-comms-only Guardrail resource.** Rejected for this pass: doubles Bedrock guardrail cost, and requires a new per-agent env-var injection path `buyer_agent_core.factory` doesn't have today — a larger architectural change than a ruleset-authoring spike should make unilaterally. Documented as a real limitation, not silently worked around.
- **Add a live `ApplyGuardrail` call inside `node_award_comms.py` against the deterministic decision text**, giving the AR check something concrete to assess on the actual critical path. Considered seriously — it's the only way to get real, non-inert AR coverage today — but deferred: it requires shaping decision-dict fields into assessable natural-language claims and choosing a synchronous-vs-async posture for a new Bedrock call on the award path, which is new application logic beyond "author a ruleset and wire it into the existing guardrail" as scoped. Left as explicit follow-up work in Results below, not silently dropped.
- **Extract rules from a prose policy document via the default `INGEST_CONTENT` build workflow.** Rejected: no such prose document exists in this codebase — `check_governance_policy`'s Python *is* the source of truth, so authoring the formal rules directly from it (`IMPORT_POLICY`) is more faithful than writing prose and re-extracting it back into logic, and skips the extraction-fidelity review cycle entirely.

## Trade-offs

| Gained | Given up |
| --- | --- |
| A real, hand-authored formalization of this system's actual award policy (not invented thresholds) — six rules traced directly to `check_governance_policy`, reviewable independent of any Bedrock build | The policy is attached to the fleet-wide guardrail, not scoped to Award & Comms specifically — the literal "applied specifically" wording of REQ-S606 is satisfied by rule semantics, not resource isolation |
| Reuses this repo's established out-of-band-boto3-for-Terraform-gaps pattern (`update_skill_runtime.py`) rather than inventing a new deployment mechanism | No Terraform resource governs the AR policy attachment — it lives outside `terraform plan`'s diff entirely (confirmed: the provider schema has no such argument, so this is invisible to drift detection, not merely undocumented) |
| The alarm and app-code wiring (`has_automated_reasoning_violation`, `_emit_automated_reasoning_failure`) are real, tested, deployed-ready code — 207/207 `buyer_agent_core` tests pass including 7 new ones | As of this ADR, the policy has not been built/validated against the live Automated Reasoning service (`deploy_automated_reasoning_policy.py` not yet run) and there is no live LLM-generated award-decision text on the critical path for it to ever assess (fact 1) — the alarm will be silent until either `award_comms_llm` re-enters Node 7's path or a standalone `ApplyGuardrail` call is added there (see Alternatives) |

## Results

`security/automated_reasoning_policy.json` (ruleset), `scripts/deploy_automated_reasoning_policy.py` (out-of-band deploy script, not yet run), `buyer_agent_core/guardrail.py`'s `automated_reasoning_findings`/`has_automated_reasoning_violation`, `serve.py`'s `_emit_automated_reasoning_failure` (wired at both guardrail-trace capture points), and `aws_cloudwatch_metric_alarm.automated_reasoning_failed` (`infra/bucket_a_alarms.tf`) added. `buyer_agent_core` test suite: 207 passed (7 new). Terraform `fmt` clean; alarm not yet applied to any environment. PRD-005 §10.7's REQ-S606 entry moved to "built, ruleset authored" pending the deploy script's run and a real LLM-generated award-decision text path — see the ADR's Alternatives section for the follow-up this surfaced.
