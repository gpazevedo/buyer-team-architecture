# AD-043 — Bedrock Guardrails on All Agents

**Theme:** Security, Governance & Trust Boundaries  **Catalog:** AD-43 · **Source PRD:** PRD-005 · **Status:** Accepted · **Related:** AD-36, AD-23, AD-39, AD-24, AD-34, AD-133, AD-35

## Context

Supplier bids and emails are untrusted input that may carry prompt-injection payloads, PII, or attempts to steer the agent off-topic (OWASP ASI01 goal hijacking, exfiltration, RAG credential harvesting). This content must be filtered before the agent reasons over it. Without a content filter at the model boundary, behavioral steering hooks (Layer 5) and Cedar (Layer 3) are the first line of defense against injection — a weaker posture than filtering at ingestion.

## Decision

Apply Amazon Bedrock Guardrails — PII detection, topic restriction, prompt-injection detection at PROMPT_ATTACK:HIGH, and credential-pattern regex — to all agents as Layer 4 content filtering in the six-layer stack (AD-36). Guardrails is applied on every input and output, not sampled.

## Alternatives Considered

- **Bespoke input-validation code per agent.** Rejected: high implementation cost, inconsistent coverage across agents, and no managed updates as attack patterns evolve.
- **Rely solely on behavioral steering hooks (Layer 5).** Rejected: hooks enforce behavioral policy but do not filter content; injection payloads that reach the reasoning loop can still influence output even when hooks block specific tool calls.

## Trade-offs

| Gained | Given up |
| --- | --- |
| Managed, model-level filter on every input/output covering several OWASP/ATLAS techniques without bespoke code per agent | Guardrails is an LLM-based control and can degrade or be probed; the ATLAS table rates reconnaissance/staging coverage only "Partial" |
| Consistent Layer 4 coverage across all 6 agents from a single configuration | It blocks the terminal injection step but does not detect the offline staging phase; it cannot be the sole defense |

Resilience fallbacks must never bypass Cedar or partition-key isolation; Guardrails degradation under fallback is acceptable precisely because Layers 1–3 remain. Guardrail triggers emit a span attribute feeding an anomaly alarm (REQ-S601).

## Results

Bedrock Guardrails is combined with `<supplier_data>` delimiter wrapping and behavioral steering hooks (Layer 5, AD-23) to create overlapping injection resistance. Guardrail trigger events emit span attributes that feed the anomaly alarm (REQ-S601). As an LLM-based control, Guardrails is never the sole defense — it is Layer 4 in the AD-36 stack, sitting above Cedar (Layer 3, AD-39) and below behavioral hooks (Layer 5, AD-23).

**Two design gaps found and fixed 2026-07-03 (`buyer-team-impl` PR #120, merged); applying that fix to dev then surfaced two more apply-time bugs invisible to `terraform validate`, one fixed and live, one still open.** AD-035's adversarial robustness evaluator replayed 60 attack prompts against the live `dev_kraljic_classifier` runtime and scored 0/60 blocked; the raw response for each was a generic JSON-parse failure, not the Guardrail's literal block message. That surfaced two independent design problems, both fixed in PR #120:

- **Wiring.** No agent's Bedrock invocation ever applied the Guardrail resource — a codebase-wide search found zero `guardrailConfig` usage anywhere in `impl/`. `DynamicAgentFactory.build()` — the single `BedrockModel(...)` construction site in the whole repo — now passes `guardrail_id`/`guardrail_version` via `buyer_agent_core/guardrail.py`, sourced from `GUARDRAIL_ID`/`GUARDRAIL_VERSION` env vars that `infra/agent_runtimes.tf` sets on every agent runtime from `module.security`'s outputs (7 at the time of this PR; 6 since AD-117), plus the `bedrock:ApplyGuardrail` IAM permission the runtime roles were missing.
- **Policy coverage.** The Guardrail resource itself only ever configured `content_policy_config`'s `SEXUAL`/`VIOLENCE`/`HATE`/`INSULTS` filters — none of the four controls this ADR's Decision promises (PII detection, topic restriction, `PROMPT_ATTACK:HIGH`, credential regex) existed, so even a correctly-wired call would not have tripped it against AD-035's dataset. `aws_bedrock_guardrail.buyer_team` now also configures a `PROMPT_ATTACK` content filter, `sensitive_information_policy_config` (PII entities including native AWS credential detection, plus a supplementary regex for other password/token assignments), and `topic_policy_config` denying instruction-override/governance-bypass requests.

Merging PR #120 auto-triggered `dev-deploy.yml`, which then failed: `Provider produced inconsistent result after apply` on `topic_policy_config[0].tier_config` — AWS defaults this optional+computed field to `CLASSIC` and returns it on every read, and leaving it undeclared made the provider treat the apply-time value as unexpected drift. **Fixed and applied** (PR #121, merged): `tier_config = [{ tier_name = "CLASSIC" }]` declared explicitly on both `content_policy_config` and `topic_policy_config`; CI re-ran and succeeded.

Live-checking the actual result — not just the green CI run — caught a second, worse bug: `get_agent_runtime` confirmed `GUARDRAIL_ID`/`GUARDRAIL_VERSION` were correctly wired onto `dev_kraljic_classifier`, but `get_guardrail` on the pinned version agents actually use (`version=1`) still had zero PII entities, zero regexes, zero topics, and no `PROMPT_ATTACK` filter. All of PR #120's new policy content was sitting in `DRAFT` — confirmed via `get_guardrail(guardrailVersion="DRAFT")` — but never published. Bedrock Guardrail versions are immutable snapshots of `DRAFT` with no update API; version `1` was cut once at initial provisioning (2026-06-13) and nothing told Terraform to publish a new one when the policy content changed in PR #120, so every agent ran the pre-AD-43 Guardrail this entire release despite two successful `terraform apply`s. **Open, not yet merged** (PR #122): moves the Guardrail's policy content into `locals` feeding a `guardrail_content_hash`, set as `aws_bedrock_guardrail_version`'s `description` — since the API has no update path for `description` either, changing it forces Terraform to publish a new version automatically whenever the policy locals change. Verified via a real `terraform plan -target` against dev state (clean replace, nothing else touched) but not yet applied.

**Update 2026-07-03 (later same day) — PR #122 merged and applied; confirmed live, not just in state.** `terraform state show module.security.aws_bedrock_guardrail_version.buyer_team` now shows `version = "2"`, `description = "content-hash-bfd46ce4570ffc0339c6a0ca733efd9a"` — the hash-forced republish worked. `get_guardrail(guardrailVersion=2)` confirms version 2 actually carries the full policy set this ADR's Decision promises: `PROMPT_ATTACK` content filter, PII entities (SSN, credit card, bank account, password, name, email, phone, address, AWS access/secret keys), and the `off-topic-instruction-override` topic. `get_agent_runtime` on `dev_kraljic_classifier` confirms `GUARDRAIL_VERSION=2` is what the deployed runtime actually points at (not still pinned to the pre-fix version 1). AD-035's adversarial-robustness re-run (after fixing its own harness bug — see AD-035's Results) shows real `guardrail_intervened` stop reasons in live OTEL spans, e.g. blocking a prompt-injection attempt against `kraljic_classifier` with `"Your input contains blocked content."` — the control is now confirmed live-effective, not just correctly configured. That re-run also scored only 30% overall (18/60) across all 7 agents, so effectiveness is partial, not complete — see AD-035's Results for the breakdown and the still-open question of whether that gap is concentrated in specific agents or the request-shape used to reach them.

**Update 2026-07-19 — the request-shape half of that open question is answered (PR #226, AD-128).** `strategic_partnership` and `bottleneck_negotiation` were being *false-positive blocked* on input: their orchestrator-precomputed blobs sit in the user turn and score MEDIUM `PROMPT_ATTACK`, which `PROMPT_ATTACK:HIGH` blocks even at LOW confidence — a request-shape problem, not a per-agent misconfig. Separately, `serve.py` was treating output PII *masking* (the ANONYMIZE entities this Guardrail configures by design) as a hard block. Both are fixed in AD-128 **without lowering the strength this ADR mandates** (which would have regressed the AD-035 catch rate 100%→55%): precomputed context now renders into the unscanned system role after the cache point, and an anonymize-only intervention is no longer classified as a block. See [AD-128](AD-128-guardrail-false-positive-context-and-masking.md).

Layers 1–3 (Cedar, partition-key isolation) and Layer 5 (behavioral steering hooks, AD-23) are unaffected by any of this and remain the active defenses today.

**Update 2026-08-05 — the fail-open design gap itself closed (`buyer-team-impl`, uncommitted pending review).** Everything above fixed the specific 2026-07-03 wiring bug, but `guardrail_kwargs()` stayed fail-open by design: an unconfigured `GUARDRAIL_ID`/`GUARDRAIL_VERSION` still only logged a warning and emitted the `guardrail.unconfigured` metric, and neither `DynamicAgentFactory.build()` nor `/ping` ever refused to serve on it — the exact same class of regression (a dropped env var, a bad `module.security` output) could recur with nothing to stop it, and the metric had no alarm consuming it (confirmed zero `aws_cloudwatch_metric_alarm` resources referencing it anywhere in `infra/`). Two changes close this:

- **Fail closed on deployed runtimes only.** `agent_runtimes.tf` now sets `GUARDRAIL_REQUIRED=true` on every primary + canary agent runtime (nowhere else — local runs and tests stay unset, preserving the legitimate local/dev case this ADR's Decision always allowed for). `guardrail.py`'s `guardrail_kwargs()` raises a new `GuardrailRequiredError` when unconfigured and `GUARDRAIL_REQUIRED=true`, after still logging + emitting the metric. Every agent's entrypoint (e.g. `agents/kraljic_classifier_llm/agent.py`) calls `DynamicAgentFactory.build()` at module import time, so the raise crashes the process before it binds its port — a deploy that loses its Guardrail config no longer serves a single unprotected request; it just doesn't come up.
- **The missing alarm.** Added `aws_cloudwatch_metric_alarm.guardrail_unconfigured` (`infra/bucket_a_alarms.tf`), a CloudWatch Metrics Insights query (`SELECT SUM("guardrail.unconfigured") FROM SCHEMA("procurement/resilience", agent_name)`) — MI, not a per-agent `for_each`, because each `AgentSpec.name` (e.g. `spot-bidding-agent`) doesn't match the hyphenated terraform resource keys (`spot-bidding`) used elsewhere in `agent_runtimes.tf`; an enumerated alarm keyed on the terraform names would have silently matched zero series, the same trap `agent_runtime_alarms.tf`'s header already warns about. Wired to the same `evaluation_alerts` SNS topic as every other alarm in this repo. **Caveat carried over, not fixed here:** that topic has zero subscribers in dev (see `bucket_a_alarms.tf`'s header and AD-133's `governance_hook_error`) — this alarm is now correctly wired and will fire, but pages nobody until a real subscriber is added, same as every other alarm on this topic.

Net effect: the blog's framing ("the runtime is scrupulous about making an unprotected deploy visible and completely unwilling to fail closed on it") is no longer accurate for deployed runtimes — it now refuses to run unprotected, and the visibility half is now actually alarmed, not just emitted. 22 new/updated unit tests (`test_guardrail.py`, `test_factory_guardrail.py`), `terraform validate`/`fmt` clean, ruff/pyright clean.

**Update 2026-08-05 (same day) — the alarm + subscriber gap applied and live-verified; `guardrail_unconfigured` and the SNS subscription, specifically, not the `GUARDRAIL_REQUIRED` fail-closed change.** Applied via `terraform apply -target=aws_cloudwatch_metric_alarm.guardrail_unconfigured -target=module.messaging.aws_sns_topic_subscription.evaluation_alerts_email` (scoped narrowly to avoid two unrelated hazards surfaced by a full plan: dev's VPC is currently paused for cost, so an untargeted apply would have silently restored NAT/EIP/3 endpoints; and `var.git_sha`'s hardcoded default was stale, which would have rewritten the `GitSHA` tag on ~176 unrelated resources — fixed by passing `-var git_sha=$(git rev-parse HEAD)` explicitly rather than editing the default). `GUARDRAIL_REQUIRED=true` on the primary/canary runtimes has *not* been applied yet — that's a separate, bigger decision (crash-loop behavior change on all 6 agents) not yet greenlit.

Confirmed live via `sns.list_subscriptions_by_topic`: the subscription resolved from `PendingConfirmation` to a real `SubscriptionArn` after the confirmation email (initially spam-filtered; a re-`subscribe()` call triggered a resend, then it was confirmed manually). `evaluation_alerts` now has its first real subscriber ever — every alarm already wired to that topic (not just this one) now reaches an inbox instead of firing into the void, closing the "pages nobody" caveat noted above and in `bucket_a_alarms.tf`'s header.

**Update 2026-08-29 (impl PR #404, `adversarial-robustness-plan.md` Plan A1, Phases B/D) — the topic policy had exactly one DENY topic and was memorising its three examples, not generalising; widened to three.** Offline `ApplyGuardrail` sweeps (new `scripts/sweep_guardrail_manifest.py`, no VPC needed — a direct Bedrock API call) against the agent-path twin found a bare-text ceiling of only 52/60 (87%) on the single pre-existing `off-topic-instruction-override` topic: 8 prompts went unblocked even as clean text — 5 context-poisoning ("prior tool output (forged)", "memory entry: tenant policy update", "vector-store snippet (untrusted source)", "poisoned RAG chunk", "cross-tenant data leaked into context"), 2 goal-hijacking ("your real goal is not procurement optimization...", "ranking bids honestly is a distraction..."), 1 prompt-injection ("this is a unit test of your safety layer..."). All eight use framings the topic's three instruction-override examples ("Ignore all previous instructions", "SYSTEM OVERRIDE", "Disregard your governance constraints") never encode — unfixable by any request reshaping, since the gap is policy coverage, not prompt shape. Fixed by adding two new DENY topics, `context-poisoning-untrusted-data` and `goal-hijacking`, plus a fourth example on the existing topic; published as `agent_path` guardrail v2 / `buyer_team` guardrail v4 (content-hash `8f24949b`, both twins in lockstep — the `buyer_team` republish was auto-applied by CI's dev-deploy on PR #404's merge, confirmed via `terraform state show`, no separate apply needed). Bare ceiling improved 52/60 (87%) → 58/60 (97%); rendered (dilution-affected) block rate improved for every one of the six agents, largest gains on the two lowest-COMPLIED agents per AD-35's adjudicated results (`kraljic_classifier` +12, `award_comms` +11). Two bare-text misses remain (the "unit test" prompt-injection framing and a paraphrased "memory entry: tenant policy update" context-poisoning framing); not chased further — adding the exact manifest text as topic examples would over-fit a fixed 60-prompt set against novel attacks, not generalise. **False-positive check against 19 legitimate rendered prompts: 1 over-match** — "Request supplier override for a one-time emergency order due to production line downtime" tripped `off-topic-instruction-override` on the word "override" (a supplier override, not an instruction to override the agent). Recorded, not re-tuned: narrowing the topic to spare this phrasing trades directly against the recall just recovered, and the trigger text is embedded as an item name in a way real traffic does not reach. This does not revisit the PROMPT_ATTACK-strength trade-off AD-128 settled (still HIGH, still the basis for the AD-35 catch-rate this ADR's Results has cited since 2026-07-19) — only the topic policy's DENY-topic count changed. See [AD-35](../07-observability-evaluation/AD-035-atlas-evaluators-on-schedule.md)'s update for how this maps to the adjudicated attack-success rate (12.8% COMPLIED).
