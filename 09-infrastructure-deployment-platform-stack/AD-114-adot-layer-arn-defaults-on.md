# AD-114 — ADOT Layer ARN Defaults On at the Root, Not via Workflow `-var`

**Theme:** Infrastructure, Deployment & Platform Stack
**Catalog:** AD-114 · **Source PRD:** PRD-004 · **Status:** Accepted · **Related:** AD-31, AD-51, AD-29, AD-121, AD-144, AD-145

## Context

`adot_python_layer_arn` gates the ADOT Lambda layer, `AWS_LAMBDA_EXEC_WRAPPER`, and X-Ray active tracing for the orchestrator node Lambdas and pr-event-router (AD-31). It defaulted to `""` and was never set by any caller, so no ADOT layer was ever attached — the resilience tracer was a no-op and every `agentcore.invoke` span was silently dropped for an unknown period before this was caught live (`Layers: []`, zero spans over a 40-minute window). The var needed a real value from somewhere. This repo's dev workflow does frequent local `terraform apply -target=...` for individual modules rather than always running a full root apply through CI, which rules out setting the value only in a CI workflow's `-var` flag: any local `-target` apply that didn't also pass the var would silently revert the layer to detached, churning tracing on and off depending on who last applied what.

## Decision

Set `adot_python_layer_arn`'s default directly in the root Terraform variable declaration to the AWS-managed us-east-1 x86_64 ADOT Python layer (`aws-otel-python-amd64-ver-1-32-0`), matching the dev runtime (python3.14/x86_64) and the `opentelemetry-api==1.32.0` pin already used in `build_orchestrator_lambda.sh`. Wire the var explicitly into every module that gates on it — the node-Lambda modules (`main.tf:116`) and, closing a separate gap, the `master-data` module (pr-event-router) which had the gating logic but was never passed the var from root.

## Alternatives Considered

- **Set the var via a CI workflow `-var` flag only.** Rejected: this repo does frequent local `-target` applies outside CI; any such apply omitting the flag would silently detach the layer, making tracing coverage depend on who ran the last apply and how.
- **Leave the default empty and require every caller to set it explicitly.** Rejected: this is the status quo that produced the silent multi-week tracing gap in the first place — an opt-in default fails open (untraced) rather than fail-safe (traced).

## Trade-offs

| Gained | Given up |
| --- | --- |
| Tracing is on by default regardless of apply path (full root apply or local `-target`), closing the class of gap that caused this outage | The ADOT layer ARN is now hardcoded to a specific AWS-managed layer version/region/arch combination in the variable default rather than threaded through as an explicit input |
| One root default lights up all currently-gated modules without per-module coordination | Upgrading the ADOT layer version or moving to a different region/arch requires editing the Terraform default rather than a workflow variable |

## Results

Verified live: node Lambdas show `Layers: [aws-otel-python-...]`, `AWS_LAMBDA_EXEC_WRAPPER` set, tracing `Active`; pr-event-router (previously `Layers: []`, `PassThrough`) now matches. A real STRATEGIC PR→PO run produced an `agentcore.invoke` X-Ray span carrying `procurement.negotiation_id`/`agent.name`/`tenant_id`/`model_id`, closing the gap described in AD-31's Results.

**Update 2026-08-21 — defaulting the ARN on does not guarantee the layer's code is the code that runs (impl PR #343).** With the layer attached exactly as this ADR intended, the orchestrator's own deployment package still bundled `opentelemetry-api==1.32.0` into `/var/task`, which precedes `/opt/python` on `sys.path` — so handlers imported a *different* api package than the one the layer's exporter was configured against, splitting the global tracer provider and silently dropping every manual INTERNAL span from X-Ray (full account in [AD-031](../07-observability-evaluation/AD-031-w3c-traceparent-propagation.md)). Fixed by removing the bundle step from `scripts/build_orchestrator_lambda.sh` — the handlers now take `opentelemetry` from the layer at runtime — and moving from the legacy layer to the optimized `AWSOpenTelemetryDistroPython:30` (embedded Lambda agent, arch-agnostic, no collector). The collector-config override PR #342 had added the day before went away with it: the optimized layer has no collector to configure. **The invariant this adds to this ADR: a build script must not vendor anything the layer also provides.**

**Update 2026-08-22 — the ARN defaults on, but `layers` is still declared per function, and nine functions never declared it (impl PR #353).** This is the bill for the update above: PR #343 removed `opentelemetry-api` from `DEPS` in `scripts/build_orchestrator_lambda.sh`, and that bundle — the very copy that was shadowing the layer on the node Lambdas — was what had been keeping the *layerless* functions importable. Removing it fixed tracing on the two functions that declared the layer and broke startup outright on the nine that did not, within hours of the same deploy. `dev-buyer-team-outbox-poller` measured **720 invocations, 720 errors in 4 hours** on `rate(1 minute)`: `Runtime.ImportModuleError: Unable to import module 'outbox_poller': No module named 'opentelemetry'`. These workers ship the orchestrator deployment package, which imports `graph_common` → `from opentelemetry import trace` at module scope, and the ADOT layer is the only thing that puts `opentelemetry` on the runtime path (`lambda_core`'s build script copies package source only, no `uv pip install --target` — [AD-145](AD-145-lambda-core-shared-platform-seam.md)). Only `node` and `comms_delivery` declared `layers`; four functions were failing on every invocation (outbox-poller, dlq-redrive, observability-heartbeat, approval-sweep) and five more were latent, failing the same way whenever they next ran (runtime-warmer, recovery, adversarial-robustness, supplier-skew, comms-bounce-handler). Fixed by attaching the layer, the three-variable App Signals opt-out ([AD-029](../07-observability-evaluation/AD-029-four-layer-observability.md)) and `tracing_config mode = "Active"` to the scheduled workers, with a programmatic check that no Lambda in the module is left layerless. `OTEL_SERVICE_NAME` is deliberately left unset — `otel-instrument` defaults it to `$AWS_LAMBDA_FUNCTION_NAME`, which is the right name for these. **A root-level default ARN removes the workflow-`-var` failure mode this ADR was written for; it does not make attachment automatic, and a missing attachment is now a hard import failure rather than merely dark telemetry.** The outage ran from PR #343's deploy late on 2026-08-21 to this fix at 15:25 UTC the next day; its operational cost is recorded on [AD-121](../07-observability-evaluation/AD-121-meta-observability-heartbeat-dead-mans-switch.md) and [AD-134](../01-orchestration-state-recovery/AD-134-scheduled-sweep-owns-approval-timeout.md).
