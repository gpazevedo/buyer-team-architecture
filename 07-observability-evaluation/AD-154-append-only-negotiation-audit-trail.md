# AD-154 — An Append-Only Negotiation Audit Trail, Fail-Open Across Three Runtimes

**Theme:** Observability & Evaluation
**Catalog:** AD-154 · **Source PRD:** PRD-004 · **Status:** Accepted · **Related:** AD-029, AD-031, AD-120, AD-121, AD-144, AD-076

## Context

`negotiations`/`bids` rows are overwritten in place each round — no history survives a re-run. Orchestrator-node decision logs go to CloudWatch with 30-day retention only. LLM agents produce a `reasoning` field, but it is a single mutable `negotiations.reasoning` value overwritten every round, and it already feeds two live LLM-as-judge scorers gating AD-034's auto-award action — any audit work has to be strictly additive, never touching that path. `REQ-O212` ("Per-Tenant Audit Trail Export") was specced against `PRDs/PRD-004-observability-evaluations-impl.md` but never deployed — a dead requirement this decision supersedes rather than revives. Tool calls — the `@tool`-decorated functions each Strands agent calls, and the MCP servers' own DynamoDB-proxy tools — were not captured anywhere beyond a bare name+status log line.

The negotiation pipeline is three genuinely separate runtimes, each already following an independent "one place boto3 is constructed" convention (`lambda_core/aws.py`, `buyer_agent_core/aws.py`, `mcp_servers/shared/aws.py`): the 6 Step Functions node Lambdas, the 6 AgentCore-hosted LLM agents, and the 3 MCP tool servers. A durable record has to span all three without collapsing that boundary into a shared package that would defeat their independent build/deploy isolation.

Two decisions were confirmed up front and compound with each other: **no TTL** (permanent retention, matching every other cross-cutting helper's behavior in this codebase) and **fail-open** on a write failure (log + metric, the negotiation never blocks). Permanent retention turns anything captured into a record that outlives the negotiation; fail-open means a *completely* broken audit path is indistinguishable from a quiet one unless something watches the failure metric itself — the 2026-08-22 outage (AD-121, AD-144) had already shown what an unalarmed emitter failure costs. Both were treated as risks to close in the same slice as the table, not follow-ups.

## Decision

**One new append-only table, `{env}-negotiation-events`, written through three independent `emit_audit_event()` copies — one per runtime — sharing an identical call signature, item shape, and metric contract, but no shared import.**

Mechanism, as shipped:

- **Schema.** Composite key `pk` = `<tenant_id>#<negotiation_id>`, `sk` = `<iso8601-microsecond-ts>#<event_id>`. A plain per-partition `Query` on `pk` returns one negotiation's full timeline, already sorted by `sk` — no GSI needed for that read. Events that legitimately carry no `negotiation_id` (category-level Kraljic work, master-data MCP proxies, pre-negotiation node decisions) date-bucket instead: `<tenant_id>#_unscoped#<date>`. Collapsing those onto a bare `<tenant_id>#` key would have made every such event fan into one hot partition.
- **Three copies, one contract.** `packages/lambda_core/lambda_core/audit.py`, `packages/buyer_agent_core/buyer_agent_core/audit.py`, `mcp_servers/shared/audit.py` each implement `emit_audit_event(*, tenant_id, negotiation_id, event_type, actor, detail, actor_identity=None)`. Each writes `item.update(actor_identity)` when present, JSON-serializes and email-redacts `detail`, truncates it, and `put_item`s with `ConditionExpression="attribute_not_exists(pk)"` (append-only — a colliding `pk#sk` is a bug, not an overwrite). Deliberately triplicated rather than a fourth shared package, for the same reason `metrics.py`/`aws.py` are already triplicated per runtime: each copy is its own isolated build artifact, and the alternative would recouple three deployments that are independent by design.
- **Fail-open.** Every write is wrapped in a bare `except Exception`; failure is logged and reported via `emit_failure_metric("audit_event", exc, namespace="procurement/audit")` — `audit_event.failure`, dimensioned only by `exception_class` — never raised. `infra/modules/observability/audit_alarms.tf` alarms on `SUM(audit_event.failure) >= 1` via a Metrics Insights `FROM SCHEMA("procurement/audit", exception_class)` query (the same pattern `bucket_a_alarms.tf` already uses for an unbounded dimension value, after two live-confirmed false starts: `PutMetricAlarm` rejects `SEARCH()` outright, and ordinary metric-math caps at 10 referenced metrics). The query's exact-dimension-set matching is a coupling the three copies must hold by convention: if any one later adds a second dimension to its failure metric, its datapoints silently stop matching this alarm while the other two keep it green — there is no test enforcing that beyond the one added later (see Results). `treat_missing_data = "notBreaching"`, since a cost-paused dev VPC producing zero audit writes is not a breach.
- **A parallel `written`/`skipped` pair for context, not alarming.** `audit_event.written` (same dimension convention, `source_layer`) fires on every successful put; `audit_event.skipped` fires when `emit_audit_event` no-ops on an empty `tenant_id` rather than collapsing onto a cross-tenant partition. Neither is alarmed — `written` exists so `skipped` has a denominator a human can read as a ratio, not so CloudWatch can compute one automatically.
- **Redaction and size, applied before every write.** `redact_emails()` recursively masks any string value under a key containing "email" and any bare email address found in *any* string value — LLM-generated prose can quote an address outside a labeled field. `_fit()` caps the serialized `detail` at 350 KB (DynamoDB's item limit is 400 KB, and `pk`/`sk`/fixed attributes count against it) — applied **after** JSON encoding, not before: wrapping a pre-encoding-sized prefix re-escapes every quote, and one measured payload grew from a 350 KB prefix to 472 KB post-wrap, past the item limit, so the write failed and fail-open silently dropped the row.
- **No read/export API in v1.** Superseding `REQ-O212`'s dead CloudWatch-Logs-Insights spec, the only read path shipped with the table was a plain per-negotiation `Query`. A GSI and a script-based reader followed later — see Results.

## Alternatives Considered

- **A shared fourth package for `emit_audit_event`.** Rejected: would recouple three runtimes whose independent build/deploy isolation (`aws.py`/`metrics.py` already triplicated per runtime) is a deliberate property, not an oversight.
- **Fail-closed on an audit-write failure.** Rejected: blocking a real negotiation on the health of its own record-keeping inverts the priority — every other cross-cutting helper in this codebase already fails open, and the negotiation's business outcome outranks the audit row.
- **Log-only, no metric, on write failure.** Rejected: fail-open plus log-only makes a 100%-broken audit path indistinguishable from a quiet one; nothing would have caught it the way the 2026-08-22 outage caught an unalarmed emitter elsewhere.
- **TTL-bounded retention.** Rejected up front: every other durable record in this codebase that matters for accountability is permanent; a time-boxed audit trail would silently stop answering the question it exists for.
- **Revive `REQ-O212`'s CloudWatch-Logs-Insights export.** Rejected: never deployed, and Logs Insights was never scoped to answer a per-negotiation or per-tenant timeline query directly — this design supersedes it rather than completing it.
- **Status quo / rely on 30-day CloudWatch log retention and the mutable `reasoning` field.** Rejected: neither survives a round overwrite or the retention window, and OKR O4's 100% audit-completeness target has no signal under either.

## Trade-offs

| Gained | Given up |
| --- | --- |
| A durable, per-negotiation, tamper-resistant timeline spanning all three runtimes, immune to the in-place row overwrites that erase `negotiations`/`bids` history | Permanent retention on a table with no size ceiling decided yet — a genuinely unbounded cost curve |
| Fail-open: an audit outage never blocks a real negotiation | Fail-open makes a total outage look identical to a quiet one unless the failure alarm itself is trustworthy — a burden this decision places entirely on `audit_alarms.tf`'s dimension-set convention |
| Redaction and truncation applied uniformly before every write, closing both a compliance gap and a hard DynamoDB item-size failure mode in the same slice | Truncation is lossy by construction — a `_truncated: true` wrapper is not the original payload |
| Three independent, build-isolated copies of the same emitter, matching the codebase's existing per-runtime convention | Three call sites to keep behaviorally identical by hand, with no shared import to enforce it — the same failure mode AD-120's correlation-id docstring already named once |
| A read path (`Query` on `pk`) shipped with the table on day one | No GSI, no export API, no content search inside `detail` in v1 — anything beyond "list this negotiation's events" was out of scope at ship time |

The permanent-retention and fail-open decisions compound rather than offset: permanence means everything captured outlives the negotiation it describes, and fail-open means the table's own health has to be independently watched (the alarm above) or that permanence guarantee is unverifiable. Neither decision is safe alone; both shipped together in slice 1 because of that.

## Results

Shipped in impl commits `4ea104a` (append-only trail across all three runtimes) and `5777071` (fixed `tenant_id` resolution for `dynamodb_master_data` tools that carry it nested inside `item`/`key`/`items[0]` rather than as a top-level kwarg — `traced_tool` needed an `_nested_tenant_id` fallback; its `Query` tool stays a structural no-op because its tenant sits inside a `key_condition` string, which turned out useful later as a cheap, side-effect-free way to exercise the skip path). Both are ancestors of `origin/main`.

**Hardening pass, closed 2026-08-30** (a post-implementation check found six live defects): PR #410 locked the test suite against real audit writes (noop across the suite, so unit tests stopped polluting the table — 333 rows purged separately); PR #412 fixed the post-encoding truncation bug above, added the `audit_event.skipped` metric, and extended email redaction to free text; PR #413 added prod-only `deletion_protection` on `negotiation-events` via a `local.protected_tables` allowlist in `infra/modules/dynamodb/main.tf` (a no-op for dev, matching this table's PITR posture — prod-only by the same default every other table gets). The check also proved the agent tier had been deployed-but-unexercised: the validation negotiation never invoked an LLM (`kraljic.source=seeded`, deterministic pricing), so `buyer_agent_core`'s emitter had zero rows until a direct invoke produced both a `tool_call` and an `agent_decision` row.

**Gap-closure pass, also closed 2026-08-30**, on eight follow-on items the hardening pass wrote down and moved past:

- §1 → PR #414 tests the failure alarm's dimension contract bidirectionally against `audit_alarms.tf`, so a drift in any of the three copies' metric shape now fails CI instead of silently un-matching the alarm.
- §2/§3/§5a → PR #415 resolves `dynamodb_master_data.Query`'s tenant (closing the one coverage hole in the trail), adds the `audit_event.written` success counter so `skipped` has a denominator, and threads `actor_identity` capture through where it is available.
- §4 → PR #417 adds `orchestrator/smoke_sfn_agents.py`, a smoke fixture that deliberately drives a real agent invocation so the agent-tier path is exercised by something other than a live negotiation with the right shape.
- §6 → PR #418 adds the GSI `tenant_time_index` (`tenant_id` + `ts`, `INCLUDE` projection on `event_type`/`actor`/`source_layer`/`negotiation_id`/`event_id` — never `detail`, which can reach 350 KB, keeping the index small on a no-TTL table) and `scripts/audit_query.py`, a CLI reader with two shapes: `negotiation` (base-table `Query`, chronological, scoped) and `tenant` (GSI, time-ranged, optionally filtered by `actor`/`event_type`, with `--detail` fetching the full row from the base table only for rows actually wanted).
- §7 → PR #416 documents alarm stickiness directly in `alarm_description`, after a live probe held the alarm in `ALARM` for 14 minutes against a single sparse datapoint — the `treat_missing_data` behavior stays *ignored* while a real datapoint still sits in the evaluation window — so a responder now reads "check the datapoint timestamps before acting" in the console instead of rediscovering the behavior.
- §8 sizing is recorded as a paragraph, not code — no automated retention-cost mechanism shipped.

**§5b — a finding, not a gap.** The Step Functions execution input carries no caller identity at all: `pr_event_router._start_workflow` builds `{tenant_id, requisition_id}` plus optional `correlation_id`/`_otel_ctx`, and the router's own `_delegated_gateway_token` docstring states outright that "PR ingest never has a human in the chain." The only human identity anywhere in the pipeline is the HITL approver's `approved_by`, and it surfaces only at award time in `orchestrator/po_delivery.py`, after every agent decision this trail records has already happened. `actor_identity` is real plumbing in all three `emit_audit_event()` signatures, but for the agent tier it is **empty by design, not deferred** — there is no orchestrator→agent identity to propagate, and no follow-on work is warranted here.

Live-verified 2026-08-30: table holds 403 rows — agent tier 277 `tool_call` + 88 `agent_decision`, actors `agent:kraljic-classifier` and `agent:leverage-auction-agent` — at roughly 15 events per negotiation (7 `tool_call` + 1 `agent_decision` + 7 `node_decision`); `tenant_time_index` is `ACTIVE`; `audit_event.written` is emitting for `lambda_core` and `buyer_agent_core` (no `mcp_servers` datapoints yet — no MCP traffic since deploy); the failure alarm reads `OK`.

Still deliberately unshipped: a `skipped`/`written` ratio alarm (needs a live baseline first), a `source_layer` dimension on the failure metric (withheld on purpose — adding it would itself break the alarm's exact-dimension-set match, see Decision), and content search inside `detail` (forked on a PITR-vs-Scan-exporter design question, not yet decided). Any future write path added to this trail must join the three existing copies' contract or risk the same silent-alarm-mismatch failure mode §1's test now guards against.
