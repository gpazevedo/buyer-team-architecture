# AD-153 — A Reserved Synthetic Tenant Runs Real Negotiations as an End-to-End Canary

**Theme:** Observability & Evaluation
**Catalog:** AD-153 · **Source PRD:** PRD-004 · **Status:** Accepted — cadence amended 2026-08-25 (hourly → daily; alarm reshaped 2-of-3 → 1-of-1) · **Related:** AD-056, AD-131, AD-119, AD-042, AD-144, AD-132, AD-121, AD-133

## Context

The platform's failure signal was layer-local. AD-121's heartbeat watches the orchestrator, AD-144's alarm registry watches every scheduled Lambda's own errors, and the domain alarms watch individual metrics — but nothing asserted the *whole pipeline* end to end on a schedule. A regression that lives in the seam between layers — a node that starts failing on the real data shape, a schema drift in a domain table, a governance overlay that stops resolving — could go unnoticed until a real negotiation hits it, and in dev there are only ~60 real negotiations a month. The trace-size monitor (impl PR #357) caught one dimension on a cadence, not the orchestration as a whole.

Task 9 of the observability plan (PRD-004) is an end-to-end synthetic canary: drive a real purchase negotiation through the orchestrator on a schedule under a reserved tenant, and assert it completes (the plan specified hourly; see the cadence amendment below). The design goal is that *nothing in the pipeline knows the canary exists* — it enters through the same master-PR DynamoDB Stream → router → ingest skill → Step Functions chain every real requisition uses, and supplier comms go to the SES mailbox simulator (`success@simulator.amazonses.com`) so sender-identity resolution, dedup and the SES send all execute identically.

The naming hazard this decision introduced is now resolved: of the three mechanisms that once shared the word "canary" — AD-56's observation window, AD-131's variant rollout, and this synthetic detector — this one keeps the bare word, because AWS owns the vocabulary (`aws_synthetics_canary`, `synthetics:canary`). AD-56's mechanism is now the *observation window* and AD-131's is *variant rollout*; "canary" (unqualified) means this Synthetics canary. The resolution is **enforced rather than asserted**: impl PR #384 added `docs/GLOSSARY.md` and `scripts/check_naming.py`, run as a "Naming gate" job on `pr-checks`, which fails the build on six *retired spellings* (`canary-observation`, `canary_observation_minutes`, `canary_traffic_pct`, `canary-by-tenant`, `drift canary`, `--rollback`). It deliberately does **not** flag the bare words — this ADR and AD-034's model-tier rollback use them legitimately, and flagging those would bury the signal in false positives.

## Decision

**Reserve tenant `canary-synthetic` and run a CloudWatch Synthetics canary that drives one real negotiation on a fixed cadence through the live pipeline, asserting terminal `AWARDED` and a winning-award composite in the 0.93–1.0 band, publishing a self-written success metric that a missing-data-breaching alarm reads.**

*Cadence amended 2026-08-25 (impl PRs #378/#380): hourly → daily, and the alarm reshaped with it. See “Alarm shape” below — the two move together or the signal degrades silently.*

Mechanism, as shipped:

- **Tenant.** `canary-synthetic` is a shared constant — `lambda_core.CANARY_TENANT_ID` — with a companion `lambda_core.is_synthetic_tenant(tenant_id)` predicate. The re-baseline countdown (`eval.threshold_rebaseline`) skips synthetic tenants through that predicate, and `kpi_rollup`'s `all_tenants` queries filter `tenant_id != canary-synthetic` because the canary completes without a human and would otherwise emit `kpi.deviated = 0` on every run, pushing `kpi.automation_rate` toward 1.0 — in dev it would *be* the series. Per-tenant queries keep the canary, so its own series stays a usable health signal. This also fixed a latent contamination the canary would have made routine: the counter's "500 *production* negotiations" contract had never been told which tenant terminated — manual e2e/smoke runs were decrementing it under the real dev tenant. The canary is the first *scheduled* stream (~720 runs/mo vs ~60 real), so a tenant predicate is the only thing that kept it from firing ~13× too often (adding the canary's 720/mo to the real 60/mo yields 780/mo, 13× the real-only rate the countdown is supposed to measure).
- **Canary runtime.** A Lambda-backed Synthetics canary on the `syn-python-selenium` runtime (chosen for its hourly `rate()` schedule; the Selenium/Chromium are bundled but unused). It is a **pure DynamoDB client** — one `PutItem` of a master PR row per run (fresh `requisition_id`), then a `GetItem` poll of the deterministic `negotiation_id` (`uuid5(tenant, "negotiation:" + requisition_id)`) to terminal `AWARDED`, then a `GetItem` of the winning award. No browser, no VPC, no separate ingress.
- **Deterministic fixtures, provisioned as code.** Category, item, two ACTIVE suppliers, category-supplier row, governance overlay and SES from-address are `aws_dynamodb_table_item` resources — no console-created records. Fixture ids are `uuid5`-derived and checked in two places that must agree: the `.tf` literals and the script's `_assert_fixtures()`, which fails the run loudly on drift. The fixture budget (`budget_override ≤ SPOT_BID_MAX_VALUE`) pins the deterministic auto-priced `SPOT_BID` path — no agent, every price/delivery a pure function of the negotiation id — and the PR's `delivery_ideal_days` is pinned to the max supplier delivery so the composite lands in [0.946, 0.975] regardless of the per-run draw. A per-tenant governance overlay pins `approval_thresholds` (auto-approve), `bid_evaluation_weights` and `Kraljic_thresholds` so the band stays deterministic while the shared default drifts.
- **Assertions.** Terminal `AWARDED`, *and* `0.93 ≤ composite_score ≤ 1.0`. The band is what converts the canary from a pure liveness probe into a weak scoring-regression detector — a change that drops composites by ~0.25 breaks real negotiations while a liveness-only canary sails through.
- **Self-published success metric.** The canary publishes `procurement/canary canary.success = 1.0` (dimension `CanaryName`) **on the PASS path only**. The Synthetics service's own `AWS/CloudWatchSynthetics` `SuccessPercent` never materialized for this canary (verified: empty namespace, no `PutMetricData` in CloudTrail despite passing runs), so "no datapoint" *is* the failure signal. The alarm reads the script's metric with `treat_missing_data = "breaching"` — a *paused* canary alarms rather than silently going green, the opposite of AD-144's `notBreaching`, because a scheduled canary that has not run is the exact thing being watched for.
- **Alarm shape (coupled to cadence).** `LessThanThreshold 1`, `Minimum`. As first shipped: 2-of-3 datapoints at hourly → MTTD ~3h against a 3-day outage, with the coupling recorded as a follow-on constraint — *if the cadence ever moves to daily, 2-of-3 becomes a two-day minimum detection, so daily requires reverting to 1-of-1*. **That constraint was exercised two days later** (impl PR #378): each run drives a full negotiation at ~$0.60, so 24 runs/day was the single largest recurring cost in dev's observability spend, and the cadence went daily for a 24× cut. The alarm moved in the same commit — `evaluation_periods = 1`, `datapoints_to_alarm = 1`, `period = 86400` — giving MTTD up to ~24h. The period is the load-bearing half: the canary publishes **only on PASS**, so an hourly period against a daily cadence would find no datapoint for ~23 hours of every day and, under `treat_missing_data = "breaching"`, alarm almost continuously. A one-line schedule change with the alarm left alone breaks the mechanism in whichever direction it moves — slower detection going down, permanent false page going up.
- **Schedule expression.** The daily cadence is `cron(0 0 * * ? *)` (00:00 UTC), not `rate(1 day)`. Synthetics' `rate()` accepts only minute and hour units — `rate(1 hour)` is its ceiling — and `UpdateCanary` rejects `rate(1 day)` with `ValidationException` (impl PR #380). The expression is duplicated in `infra/enable_canary_cron.sh`, which must track `synthetics_canary.tf` as the source of truth.
- **Cleanup.** `canary_cleanup` — a daily scheduled Lambda — deletes canary-tenant rows older than `RETENTION_DAYS` (14) from the seven domain tables that carry no TTL: negotiations, bids, awards, communications, orders, test-tenant-orders, and requisitions (the last added because the router's `_upsert_domain_requisition` writes it for every claimed master row). TTL is deliberately **not** enabled: DynamoDB only expires items carrying a `ttl` attribute, and stamping one would mean teaching the *production* write paths about synthetic tenants — the property the mailbox-simulator choice protects. Where `tenant_id` is the partition key (negotiations/bids/awards) a `Query` is bounded to the canary's partition instead of scanning; the prefixed-`pk` tables genuinely require a `Scan`. The Lambda registers in AD-144's scheduled-Lambda alarm map and emits `canary_cleanup.failure` via `lambda_core`'s `guarded()`.
- **M2M identity.** Two dedicated Cognito App Clients (`pr_event_router_canary`, `po_export_canary`) are bound to the canary tenant through the same `COGNITO_CLIENT_MAP` / `PO_EXPORT_CLIENT_MAP` mechanism AD-119/AD-042 established, so canary JWTs mint `tenantId = canary-synthetic` — never the dev tenant id. A `{pk: canary-synthetic, sk: tenant}` binding row completes the pre-token V3 normaliser's lookup.
- **Environment coupling.** `release_vpc.sh` / `restore_vpc.sh` discover pausable schedules by a `Pausable = true` tag, so the canary suspends with the environment rather than alarming through a teardown. **Tag discovery alone proved insufficient on two counts, both found by running it** (impl PRs #377, #381):
  - *Stop is not idempotent.* `stop-canary` against an already-`STOPPED` canary returns `ConflictException`, and under `set -euo pipefail` that aborted `release_vpc.sh` **before the terraform teardown ran** — so a re-run of the pause script left NAT, EIP and the interface endpoints billing while appearing to have paused the environment. Both scripts now read `Canary.Status.State` first and act only from `RUNNING`/`STARTING` (stop) or `STOPPED`/`READY` (start).
  - *Stopping does not disarm the schedule.* A stopped canary keeps its cron; a later broad `terraform apply` re-asserts `synthetics_canary.tf` (cron **and** `start_canary = true`) and restarts a daily canary inside a paused window. `release_vpc.sh` now sets the schedule to `rate(0 hour)` — Synthetics' documented “run once per start, never recurring” value — *before* stopping. Restoring it needs a real expression, so `infra/enable_canary_cron.sh` owns that half and `restore_vpc.sh` delegates to it, keeping one copy of the restore path.
  
  The alarm side of the pause is not the canary's own: the `${ENVIRONMENT}-buyer-team-` alarm sweep of [AD-133](../08-cost-architecture-optimization/AD-133-delete-and-replay-dev-alarms-across-pause.md) silences it, which is why a deliberate pause does not page despite `treat_missing_data = "breaching"`. That prefix is load-bearing — renaming the alarm out of it re-arms the page.
- **Artifacts.** A dedicated S3 bucket with a 30-day lifecycle (the canary's per-run folders match), plus 30-day success/failure retention periods. No existing bucket fit — `procurement_data` is the dataset store and `dlq_archive` is a 7-year WORM archive.

## Alternatives Considered

- **A browser-based Synthetics canary (full UI walk).** Rejected: the pipeline's real entry point is a master-PR row write, not a browser, so a UI walk would exercise its own Selenium path instead of the ingest path and add runtime cost and fragility. The Lambda-backed canary uses the scheduled runtime but stays a pure DynamoDB client on the exact production entry.
- **Liveness only (assert terminal `AWARDED`, no score band).** Rejected: a scoring regression that still completes would sail through; the band is what gives the canary its ability to catch the failure mode that matters most for evaluation integrity.
- **Enable DynamoDB TTL on the domain tables for canary cleanup.** Rejected: TTL only expires items that carry a `ttl` attribute, so production write paths would have to stamp one — teaching them about synthetic tenants, the property §9a Q2 exists to protect.
- **Send canary supplier comms to a real mailbox, or bypass the send.** Rejected: the mailbox simulator runs sender-identity resolution, dedup and the SES send identically; a bypass or real address would either teach the code the canary exists or pollute real mail.
- **Reuse the dev tenant for the canary.** Rejected: the canary completes without a human, so it would distort `automation_rate` (and the re-baseline countdown), and its rows would mingle with real data in the no-TTL tables.
- **Status quo / rely on the existing layer-local alarms and the trace-size monitor.** Rejected: each watches a single layer or dimension; nothing asserted the whole DAG on a schedule, and at ~60 real negotiations/month a full-pipeline regression could go unnoticed for days.

## Trade-offs

| Gained | Given up |
| --- | --- |
| A real end-to-end liveness + weak scoring-regression signal on a schedule, exercising the exact production path with nothing in code aware of it | A reserved tenant whose rows must be swept from seven no-TTL domain tables by a dedicated daily cleanup Lambda |
| Daily cadence costs ~$0.60/day instead of ~$14.40/day, which is what makes the canary affordable to leave running | MTTD up to ~24h, and a schedule/alarm pair that must be changed together — one without the other degrades or falsely pages |
| The canary asserts the composite band, catching scoring regressions that pure liveness would miss | Fixture rows live in *real* domain tables — a `terraform apply` can now drift/revert them mid-negotiation, and a fixture-id change is a coordinated code + `.tf` change |
| Synthetic traffic is excluded from KPIs and the re-baseline counter by one shared predicate, so it can neither distort the metrics nor flood the countdown | An exclusion clause now baked into every `all_tenants` KPI query, plus a CI naming gate carrying a hand-maintained list of retired spellings (the third "canary" concept is resolved, not free) |
| Full comms path exercised via the SES mailbox simulator | Canary rows age in domain tables for up to `RETENTION_DAYS` (14) before cleanup |

The alarm's `treat_missing_data = "breaching"` is a deliberate inversion of AD-144's `notBreaching`: a scheduled Lambda that *hasn't run yet* is a normal fresh-deploy condition there, but for a canary that must fire every hour, missing data is the failure. The metric-publishing decision deserves its own caveat — the canary self-publishes because the managed `CloudWatchSynthetics` `SuccessPercent` never appeared, so the alarm's correctness depends on that managed metric remaining absent-or-ignored; if Synthetics ever starts publishing it, the alarm still reads only the script's metric and the two must not be confused.

## Results

Shipped across impl PRs **#364–#369, #370, #373–#376** (Task 9, observability-plan v4 §9g): `lambdas/synthetics_canary/python/canary.py`; `infra/modules/observability/synthetics_canary.tf` (canary, fixtures, governance overlay, alarm, artifact bucket); `lambdas/canary_cleanup/` + `infra/modules/observability/canary_cleanup.tf`; the `kpi_rollup` exclusion clause; the `is_synthetic_tenant` predicate in `lambda_core.constants` consumed by `orchestrator/eval_rebaseline_metrics.py`; the two M2M clients and tenant-binding rows in `infra/gateway.tf`, `infra/main.tf`, `infra/modules/security/`; and the pause-by-tag VPC-script changes. `canary_cleanup` joined the scheduled-Lambda map of [AD-144](AD-144-scheduled-lambda-errors-alarm-registry.md).

Live-verified on dev 2026-08-23: the canary passes with terminal `AWARDED` and a composite in band, and the alarm reads the self-published `procurement/canary` metric (the managed `SuccessPercent` remains absent, confirming the self-publish was necessary). A `terraforming-race` on the very first apply (fixture rows created concurrently with the canary) was fixed by `depends_on` the fixture items, and the canary script had to sit under `python/` in the zip for the Synthetics runtime — both recorded in the module.

**2026-08-25 (impl PRs #377–#381) — the first week of operation moved the cadence and rewrote the pause path.** Three of this ADR's own follow-on constraints came due at once:

- *The cadence-to-alarm coupling was exercised, as written.* Hourly ran ~720 negotiations/month at ~$0.60 each; PR #378 cut it to daily and reshaped the alarm to 1-of-1 with `period = 86400` in the same commit, exactly as this ADR said daily would require. PR #380 then found the mechanical constraint the plan had not: Synthetics' `rate()` tops out at `rate(1 hour)`, so `rate(1 day)` is rejected by `UpdateCanary` and the daily cadence had to be expressed as `cron(0 0 * * ? *)`.
- *Pause-by-tag was necessary but not sufficient.* PR #377 fixed a defect with a cost consequence well outside the canary: `stop-canary` on an already-`STOPPED` canary raises `ConflictException`, which under `set -euo pipefail` killed `release_vpc.sh` **before the terraform teardown**, so a second pause attempt silently left NAT/EIP/endpoints billing. PR #381 then closed the schedule half — a stopped canary keeps its cron, and a broad apply re-arms it — by disabling the schedule to `rate(0 hour)` before stopping and adding `infra/enable_canary_cron.sh` as the single restore path that `restore_vpc.sh` delegates to. PR #379 backfilled `test_vpc_scripts_ordering.py` for both guards.
- *The naming hazard is now guarded.* The retitles landed in adr PR #60; impl PRs #383/#384 finished the code and prose and added the `pr-checks` naming gate described in Context, so the resolution survives contributors who never read this ADR.

Follow-on constraints this decision creates: the cadence-to-alarm coupling (changing the schedule without changing `evaluation_periods`/`datapoints_to_alarm`/`period` silently weakens MTTD in one direction and false-pages in the other), the cron expression duplicated between `synthetics_canary.tf` and `enable_canary_cron.sh`, the fixture-drift discipline (`.tf` literals and `_assert_fixtures` must move together), the `${ENVIRONMENT}-buyer-team-` alarm-name prefix that AD-133's pause sweep depends on, and the standing rule that any future synthetic stream joins the `is_synthetic_tenant` predicate or it will contaminate the same KPIs the canary was excluded from.
