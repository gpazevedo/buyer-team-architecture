# AD-161 — The Oracle Spec Is the Contract; the Tool Surface Is Generated From It and Guarded in CI

**Theme:** Integration (Skills, Plugins & Transports)
**Catalog:** AD-161 · **Source PRD:** PRD-011 · **Status:** Accepted · **Related:** AD-68, AD-155, AD-158, AD-160

## Context

The Oracle integration has three consumers of one description of Oracle Fusion's REST API: the MCP tool surface the Gateway serves (AD-160), the emulator that stands in for a real Fusion pod in dev, and the response validation the tests assert against. Nothing forces those three to agree unless something upstream of all of them is authoritative.

The usual failure mode is the spec drifting to accommodate the code — a response doesn't validate, so the schema is widened; a tool count is inconvenient, so an operation's shape is edited. Each such edit is invisible afterwards, because every downstream artifact is regenerated from the edited spec and agrees with it perfectly.

Two specific hazards made this concrete here. `generated/oracle_tools.py` is a checked-in generated file, so a hand-edit to it looks exactly like a legitimate change in review. And the CI that was supposed to prevent that never ran: `buyer-team/.github/workflows/oracle-codegen.yml` sat in a directory that **is not a git repository**, while the `oracle` repo had no `.github/` at all — so the sentence "CI fails on any diff", on which the whole discipline rested, was false everywhere it was written.

## Decision

**`oracle/spec/*.json` is the contract; everything else is downstream of it, and CI enforces that.**

- **Direction of travel is spec → emulator, never emulator → spec.** The emulator serves the spec files verbatim at `/describe` and never introspects its own routes. If a response fails validation, *the emulator is wrong*. The spec does not move to make a test pass.
- **The only permitted edit to a spec after the emulator exists is subtractive** — deleting a whole path to control tool count. Additive or corrective edits are a Phase 7 reconciliation against a live pod, not a convenience.
- **`generated/oracle_tools.py` is never hand-edited**; it is regenerated by `tools/codegen.py`, whose output is deterministic and version-controlled.
- **The guard lives in the `oracle` repo, not beside it.** `oracle/.github/workflows/ci.yml` runs `uv run python tools/codegen.py --check` (non-zero on any diff between the generated file and the specs), imports `TOOLS` to prove the generated module is loadable, and runs the spec/emulator/MCP-server suites. Path filters and commands are rebased to that repo's root; a `pyproject.toml` makes the repo self-contained so `uv` resolves its own dependencies rather than an out-of-tree virtualenv.

**And the guard was proven by breaking it, not by reading it.** A scratch branch perturbed one parameter name in a spec file and confirmed CI went **red**; the perturbation was then reverted. An unproven guard is the thing this decision exists to fix.

## Alternatives Considered

- **Fix the workflow in place under `buyer-team/.github/`.** Rejected: that directory is not a git repository and never has been, so nothing in it can execute anywhere. Its path filters (`oracle/spec/**`) and commands assumed the `buyer-team` root, so even a straight copy into the `oracle` repo would not have run. The directory was deleted rather than repaired.
- **Generate the tool surface at runtime instead of checking it in.** Rejected: a checked-in generated file makes the surface reviewable in a diff and lets `--check` be a cheap CI assertion. Generating at import time would hide surface changes entirely and move a build-time failure into the deployed runtime.
- **Treat the emulator as the source of truth and derive the spec from its routes.** Rejected — it is the drift this decision forbids, wearing a tidier hat: every test would pass against whatever the emulator happens to do, which is the one thing that cannot validate an integration with somebody else's API.
- **Hand-maintain the tool list, using the spec as documentation only.** Rejected: three consumers, one of them a deployed MCP server, and no mechanical link between them.

## Trade-offs

| Gained | Given up |
| --- | --- |
| One authoritative description; the tool surface, the emulator and response validation cannot silently disagree | Every legitimate spec change is now a two-step (edit, regenerate) with a CI gate, and the subtractive-only rule makes a genuine correction deliberately awkward until Phase 7 |
| A hand-edit to the generated file fails CI on the next push, in the repo that owns it | The guard covers only what the spec constrains — see below |
| Proven red on a real perturbation, not asserted | The proof cost a scratch branch and a deliberately broken CI run |

**The blind spot is worth naming precisely, because it is structural.** The spec's component schemas carry no `required` lists, so *renaming a response field* changes neither the generated tools nor any assertion in `test_surface.py` — the guard stays green. Parameter names are caught (they flow into a tool's `inputSchema`, which is exactly what the perturbation proved); response field names are not. This matters more than it sounds: `oracle/spec/*.json` is transcribed from Oracle's published REST reference, not fetched from a running pod, and codegen, the emulator and validation are all downstream of it. A wrong field name is therefore *self-consistently invisible* — every test passes and the first real call fails. That is the one defect the whole green suite structurally cannot catch, and the reason Phase 7 (fetch `/describe` from a live pod with `Accept: application/vnd.oracle.openapi3+json`, reconcile **code to spec**, record the fetch date) stays on the plan.

## Results

Landed as `buyer-team-oracle#2`: `oracle/.github/workflows/ci.yml` with filters on `spec/**`, `tools/codegen.py`, `generated/oracle_tools.py`, `emulator/**`, `mcp_server/**`, `tests/**`, `pyproject.toml` and `uv.lock`; a `pyproject.toml` making the repo self-contained; and the deletion of the unreachable `buyer-team/.github/`. Proven by perturbation on a scratch branch (red, then reverted and the branch deleted). The workflow has run green on every subsequent oracle PR — `#3` (Lambda image), `#4` (MCP server, which added `tests/test_mcp_server.py` to the run) and `#5` (Runtime image).

Two limits of the current wiring, recorded rather than glossed: CI runs `tests/test_surface.py` and `tests/test_mcp_server.py` only — `test_oracle_integration.py` needs the private impl repo checked out as a sibling and so cannot run there. And the "spec is the contract" rule is stated in `old_oracle_plan/README.md`, which Phase 0 deliberately demoted to history; this ADR and the forthcoming `oracle-integration.md` are where it now lives. The generated surface this guards is the same 23 tools AD-160's Gateway serves, which is what makes the spec the contract on *both* sides of the MCP wire rather than only inside the repo.
