# AD-157 — Supplier-MCP Discovery + Registration: a Real Endpoint to Probe, Not a Bool

**Theme:** Integration (Skills, Plugins & Transports)
**Catalog:** AD-157 · **Source PRD:** PRD-011 · **Status:** Accepted · **Related:** AD-138, AD-146, AD-155, AD-156

## Context

`channel.select_channel` (AD-138) has named `Channel.SUPPLIER_MCP` since the delivery path first shipped, but every branch resolved to EMAIL: `tenant_id`/`supplier_id` were accepted and immediately discarded (`del tenant_id, supplier_id`), and `supplier_mcp_registered` was a bare bool no caller ever set to `True`. The gap wasn't the channel-selection logic — it was that "auto-discovery + fallback" only had its fallback half built. `get_supplier_mcp_breaker()`/`mark_suppliers_unreachable()` (PRD-006 §2.2) already existed for the case where a registered MCP transport goes unreachable; nothing existed to register one in the first place, and PRD-011 §3.3's `discover_supplier_mcp`/`register_supplier_mcp` tools were designed (signatures fixed in `PRD-011-integration-skill-impl.md`) but never implemented. With no real Supplier MCP server anywhere in the stack — not even a mock — there was also nothing to probe against, mirroring the position `sap/`'s CDS mock filled for the SAP integration before AD-155's gap-closure work.

## Decision

Four pieces, landed together, that turn the named-but-unused channel into a real one:

1. **A minimal supplier emulator**, `mcp_servers/supplier_mock/`, exposing exactly PRD-011 §3.3's seven required tools (`receive_bid_invitation`, `submit_bid`, `receive_clarification_request`, `receive_follow_up`, `receive_award_notification`, `receive_rejection_notification`, `acknowledge_purchase_order`) via `mcp_servers/shared`'s `build_mcp_app()` factory (AD-146), so it inherits AgentCore context middleware, observability, and `/ping` the same way `tenant_mdm_emulator` does. Unlike that AgentCore-Runtime server, this one is deployed exactly like `sap_mock.tf`: a container-image Lambda behind a public, unauthenticated Function URL, $0 at rest, standing in for an external supplier's own server rather than one of this repo's own domains. It is deliberately stateless — every tool returns a fixed acknowledgement — because its job is to prove discovery, registration, and breaker-triggered fallback, not to simulate supplier negotiation behavior.
2. **Registration lives on the `{env}-suppliers` row**, as a new `mcp_registration` map (`mcp_endpoint`, `auth_type`, `auth_credential_ref`, `discovered_tools`, `contract_version`, `status`, `last_probed_at`). That table is already per-tenant and already the natural home for a supplier's transport metadata; `{env}-system-config`'s `registry` group was rejected (see below).
3. **`discover_supplier_mcp`/`register_supplier_mcp`** land in `skill_runtime/server.py`, matching the signatures PRD-011-integration-skill-impl.md §2.3 already specifies. Both probe the registered endpoint with a real MCP `initialize` + `tools/list` — using the `mcp` SDK's client directly (`streamablehttp_client` + `ClientSession`), not `orchestrator.mcp_gateway_client.GatewayClient`. That class's `call_tool`/`list_tools` speak AgentCore Gateway's own wire shape (`{gateway_url}/{gateway_target}/invocations`, Cognito M2M auth) — correct for Gateway-fronted targets, and `list_tools` was added there too (sharing `call_tool`'s JSON-RPC POST + SSE-unwrap via a new `_post_jsonrpc` helper) since a Gateway-fronted MCP target's tool list is a real, general need. But a supplier's own server, reachable directly over plain MCP-over-HTTP with no Gateway in front, needs the SDK's actual client-session handshake instead of that Gateway-specific framing — using `GatewayClient` here would silently assume a wire contract the target doesn't speak. A registered-but-unreachable or protocol-mismatched supplier fails the probe as `UNAVAILABLE`/`VALIDATION_FAILED` rather than raising; `AVAILABLE` requires all seven tools, `DEGRADED` covers a reachable server missing one or more.
4. **`select_channel` reads `mcp_registration.status` directly** (a DynamoDB point read against `{env}-suppliers`) instead of taking a caller-supplied bool — the registration lookup belongs where the routing decision is made, not threaded through every call site as a pre-resolved flag nobody was actually resolving. Only `AVAILABLE` routes to `SUPPLIER_MCP`; `DEGRADED` falls back to EMAIL rather than risk calling a tool the supplier's server doesn't implement. The circuit-breaker check stays a caller-injected `supplier_mcp_breaker_open` bool, since this package still never imports `pybreaker` (AD-138) — `orchestrator/comms_delivery.py` computes it from `get_supplier_mcp_breaker().current_state`.

The actual SUPPLIER_MCP send lands inside `deliver_communication`/`approve_and_deliver` themselves — **the same governed path, not a second one** (AD-138's whole reason for existing). A new `supplier_mcp_transport.py` module (parallel to `ses_transport.py`) does the real MCP `tools/call`, again via the SDK client directly; `comm_type` maps to one of the five buyer→supplier notification tools (`submit_bid` is supplier-initiated, `acknowledge_purchase_order` is PO-export's concern — neither has a `comm_type` analog), and a `comm_type` with no mapping fails closed rather than guessing a tool name.

## Alternatives Considered

- **Store the registration on `{env}-system-config`'s `registry` group instead of `{env}-suppliers`.** Rejected: that group is system-wide, not per-tenant, and repurposing it for per-supplier data would need a `config_schema` MAJOR version bump for data that doesn't structurally belong there. `{env}-suppliers` already carries `source_system_ids` and is already keyed per-tenant/per-supplier.
- **Reuse `GatewayClient` for the direct supplier probe, adding a "no-Gateway" mode to it.** Rejected: `GatewayClient`'s whole value is Cognito M2M token caching for an AgentCore Gateway's fixed URL shape. Bending it to also skip auth and POST to an arbitrary supplier URL would blur what the class guarantees callers, for a wire protocol (plain MCP session handshake) it doesn't actually implement — the SDK's own client does that correctly already.
- **Make `mcp_servers/supplier_mock` a genuine AgentCore-Gateway `mcp`-type target now, unlocking per-tool Cedar actions.** Deferred, not rejected: the emulator's Function URL is an HTTPS endpoint and could be exactly that — the repo's first `mcp`-type Gateway target, per `mcp_gateways.tf`'s own note that no current target can exercise per-tool actions. Out of scope here; discovery/registration/fallback are provable without it, and per-tool Cedar authorization is a real but separable follow-up.
- **Skip a real emulator and hand-wave discovery with a hardcoded fixture.** Rejected: `discover_supplier_mcp`'s whole job is a live `tools/list` against a real endpoint. Faking the response would prove the DynamoDB read/write plumbing but not the actual MCP client code path, or the "kill the emulator, fall back to EMAIL via the breaker" acceptance case this feature exists for.

## Trade-offs

| Gained | Given up |
| --- | --- |
| A real, discoverable Supplier MCP endpoint to probe and send through, closing the "auto-discovery" half PRD-011 always specified but never got | A second live MCP client code path (`mcp` SDK direct) alongside `GatewayClient`'s Gateway-fronted one — two ways this repo talks MCP, not one |
| `DEGRADED` (reachable, missing a required tool) fails closed to EMAIL rather than guessing which of the seven tools are safe to call | A supplier missing even one required tool gets no MCP traffic at all, even for comm_types its present tools could serve |
| One send path for both EMAIL and SUPPLIER_MCP (AD-138 preserved) | `deliver_communication`/`approve_and_deliver` each now branch on three outcomes (EMAIL/SUPPLIER_MCP/unavailable) instead of two |
| No Token Vault dependency to stand up before this could ship | `auth_type: API_KEY` treats `auth_credential_ref` as a literal bearer token today; `OAUTH2`/`MUTUAL_TLS` registrations probe with no auth at all and fail honestly rather than being rejected outright |

## Results

Implemented in `mcp_servers/supplier_mock/` (server + Dockerfile), `infra/supplier_mock.tf` + `infra/ecr.tf` + `.github/workflows/dev-deploy.yml` (build/deploy wiring mirroring `tenant-mdm-emulator`'s CI shape, deploying like `sap_mock.tf`), `orchestrator/mcp_gateway_client.py` (`list_tools` + shared `_post_jsonrpc`), `skill_runtime/server.py` (`discover_supplier_mcp`/`register_supplier_mcp` + `skills/integration/SKILL.md`), and `packages/supplier_comms/` (`channel.py`'s registration read, new `supplier_mcp_transport.py`, `delivery.py`/`approval.py`'s SUPPLIER_MCP send branch, `orchestrator/comms_delivery.py`'s breaker injection). Offline test coverage: `orchestrator/tests/test_mcp_gateway_client.py`, `skill_runtime/tests/test_supplier_mcp.py`, `packages/supplier_comms/tests/test_channel.py` and `test_delivery.py`'s new SUPPLIER_MCP cases — all against fakes/moto, no live AWS or network calls.

Live-verified end to end against the deployed emulator (2026-09-05, after finding and fixing three separate deploy bugs the offline test suite couldn't catch — a Lambda architecture mismatch, a `.dockerignore` exclusion, and a missing runtime dependency; impl PRs #457–#459): `discover_supplier_mcp` returns `status: AVAILABLE` with all seven tools, `select_channel` picks `SUPPLIER_MCP`; killing the emulator (reserved concurrency pinned to 0) drives the real `supplier_mcp` breaker open after five genuine failures (CloudWatch EMF confirms the `circuit_breaker.state_change → open` metric), and `select_channel` correctly falls back to `EMAIL`. Per PRD-011 §3.3's own note, real suppliers' `OAUTH2`/`MUTUAL_TLS` credentials still have nowhere to resolve from until a Token Vault exists.
