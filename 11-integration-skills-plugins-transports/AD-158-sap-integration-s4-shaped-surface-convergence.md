# AD-158 — SAP Integration Converges Both Transports on the S/4-Shaped Surface

**Theme:** Integration (Skills, Plugins & Transports)
**Catalog:** AD-158 · **Source PRD:** PRD-011 · **Status:** Accepted · **Related:** AD-68, AD-97, AD-155, AD-156, AD-159

## Context

Before this decision, direct-HTTP SAP calls (`sap_ingest`/`po_export_drain`/`sap_supplier_map`/`sap_pr_poller`) and the MCP-transport calls (`sap_odata_mcp.py`, gap-closure plan Phase 3) each read a different bespoke OData surface — `/odata/v4/procurement` for direct HTTP, a separate V2-adapter shape for the MCP catalog — neither named the way a real SAP S/4 system names its entities or fields. Both surfaces also forced a client-side step a real S/4 system doesn't need: the direct-HTTP write path resolved a purchase order line's SKU to an internal `Materials.ID` by re-fetching the source PR with a 3-level `$expand` and building a `materialNumber -> ID` map (`_fetch_sap_pr`/`_material_by_number`) before it could POST, purely because the old surface's `PurchaseOrders.items` association needed a real id, not a SKU string; the MCP path carried its own N+1-read shape for the same reason, compounded by AWS's `odata_read` tool having no `$expand` argument to compensate with. The two transports therefore couldn't share a single item-building function even though they wrote the same logical fields, and every subsequent phase of this integration (Phase 5's master-data participation, Phase B/C's transport-parity and DLQ work) would otherwise have had to keep reasoning about two independent, both-non-standard contracts.

## Decision

Migrate both transports onto one shared, S/4-shaped OData surface — real S/4 entity and field names (`A_PurchaseRequisition`/`A_PurchaseRequisitionItem`/`A_PurchaseOrder`/`A_PurchaseOrderItem`/`A_Product`, `PurchaseRequisitionPrice`/`DocumentCurrency`/etc.) served by `buyer-team-sap`'s new mock surface — direct HTTP at its V4 endpoint (`/odata/v4/s4-procurement`), the MCP catalog at its V2 endpoint (`/odata/v2/s4-procurement`), each transport keeping the OData version its own client library already spoke. Three consequences follow from matching the real shape:

1. **SKU resolution moves server-side.** `A_PurchaseOrderItem.Material` carries the SKU string directly; the mock's write-side handler (`s4-procurement-service.js`) resolves it to an internal id the way real S/4 create semantics do. `po_export_drain._build_po_items` drops its `material_by_number` parameter entirely — the 3-level-`$expand` PR refetch that fed it is gone from the direct-HTTP path.
2. **Both transports converge on the same item-building code.** Once both speak the same field names, `_build_po_items` is shared verbatim between the direct-HTTP deep-insert payload and the MCP path's per-item `odata_create` calls (gap-closure plan 3.3's shared-shape goal, only actually reachable once the shapes agreed) — and the MCP read side collapses from four reads to two, since `A_PurchaseRequisitionItem` already flattens `Material`/`MaterialGroup` onto the row.
3. **Two client behaviors the real surface demands that the old one never did.** `sap_client.py` gains per-path ETag memory, replayed as `If-Match` on the next write — the mock's V2 adapter rejects a PATCH without one (HTTP 428), stricter than the old surface ever was. And a 400 response is now raised as `SapTerminalError` (an `httpx.HTTPStatusError` subclass) instead of retried — a SAP business-rule rejection (an unmapped SKU, a bad reference) cannot succeed on retry, so `po_export_drain` routes it straight to `PO_EXPORT_DLQ_URL` instead of burning three attempts first (the DLQ this decision creates, later generalized into AD-156's `dlq_consumer` engine).

The migration landed in two PRs because the transports could move independently without either blocking on the other: direct HTTP first (impl PR #437, gap-closure Phase 4.1–4.3), then the MCP catalog and `sap_via_mcp`'s default flip to `true` (impl PR #448) once `sap_mcp.tf`'s catalog registration was repointed at the same surface — direct HTTP staying the automatic fallback on any MCP exception throughout, unchanged by this decision. Impl PR #452 (gap-closure Phase B) then extended the same converged shape to the three reads Phase 4 hadn't touched — `fetch_material_prices`/`fetch_suppliers`/`fetch_purchase_orders` — giving `sap_odata_mcp.py` MCP-transport counterparts for all of them and wiring the identical MCP-with-direct-HTTP-fallback dance into `skill_runtime/server.py`'s ingest path, which had no `SAP_VIA_MCP` gating of any kind before that PR.

## Alternatives Considered

- **Keep the two bespoke surfaces and add the DLQ/ETag handling to each independently.** Rejected: leaves the actual problem — two non-standard contracts, no shared item-building code — in place, and every future phase would keep paying the 3-level-`$expand`/N+1-read tax this decision removes.
- **Move only the direct-HTTP path, defer the MCP catalog indefinitely.** This is what impl PR #437 itself did as an intermediate state (`sap_odata_mcp.py` and `sap_bridge.py` "deliberately left on the old surface," per that PR's own summary). Rejected as a permanent end state: it would leave `sap_via_mcp=true` unable to ever collapse `_build_po_items` or the N+1-read shape. It was a sequencing choice — avoid bundling a live-MCP-Gateway-facing change with a mock-schema change in the same PR — not a design one, and PR #448 completed the migration the same day.
- **Version the old and new surfaces behind a permanent runtime flag.** Rejected: the old `/odata/v4/procurement` and `/odata/v2/procurement` surfaces stay live only because both mock services still project the same underlying tables during the transition, per `sap_client.py`'s own header comment — a deliberate migration aid, not a supported dual-contract design. Nothing in this decision commits to maintaining two surfaces long-term.

## Trade-offs

| Gained | Given up |
| --- | --- |
| Both transports read and write one real-shaped contract — no more independent field-naming schemes to keep in sync as the integration grows | A live run against the deployed sapmcp Gateway on the new catalog shape was still outstanding at merge (needs the dev VPC restored) — proven offline via a Floci rig (10/10) and the direct-HTTP path's live PO-export drain, not yet via a real MCP round trip |
| SKU resolution is now the mock's job, not the orchestrator's — deletes the `_fetch_sap_pr`/`_material_by_number` round trip and ~85 lines of MCP-only shape-resolution code (PR #448) | `sap_client.py` now tracks per-path ETag state across calls — a small piece of session-like memory a stateless client didn't need to carry before |
| A 400 is classified (`SapTerminalError`) instead of retried blindly, so a business-rule rejection reaches the DLQ in one round trip instead of three | Two OData versions still exist for the two transports (V4 direct-HTTP, V2 MCP) — this decision unified the *entity/field shape*, not the wire version each client speaks |

## Results

`orchestrator/sap_client.py` (`DEFAULT_SAP_BASE_URL`, `SapTerminalError`, `_etags`), `sap_ingest.py`/`sap_pr_poller.py`/`sap_supplier_map.py`/`po_export_drain.py` (S/4 entity names; `_build_po_items` without `material_by_number`), `sap_odata_mcp.py` (`ENTITY_PRS`/`ENTITY_PR_ITEMS`/`ENTITY_POS`/`ENTITY_PO_ITEMS`/`ENTITY_PRODUCTS`; four-read → two-read `fetch_pr`), `infra/sap_mcp.tf` (`sap_via_mcp` default flipped `false` → `true`), `infra/modules/step-functions/{main,variables}.tf` (`po_export_dlq_arn` output plus IAM/env wiring for the DLQ fast path). Verified offline: 775/775 `orchestrator` unit tests and a 10/10 Floci rig run against a rebuilt `sap-mock` image on the new surface (PR #448), 218/218 targeted plus 2354/2356 full-suite (2 pre-existing, unrelated flakes) after Phase B's extension (PR #452). `terraform validate`/`plan` clean on all three PRs. Enables gap-closure Phase 5's master-data participation (impl PR #443) and AD-159's catalog-price baseline, both of which read `A_Product` — a table the old surface never exposed as a first-class entity. Still open: a live run against the deployed sapmcp Gateway on this catalog shape — every SAP PR through impl PR #461 keeps landing behind the same "needs the dev VPC restored" gate, offline and mock-verified only.
